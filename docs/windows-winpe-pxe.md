# Windows 10: первая проверка WinPE по PXE

[English version](en/windows-winpe-pxe.md)

> 20.10.2026 этот статический пункт, локальная копия ISO и шара `windows10` удалены; Windows 10 загружается через профиль ISO (см. [руководство Images](images-installation.md)). Ниже — история первой проверки.

Эта порция добавляет в загрузочное меню Windows 10 x64 и загружает `sources/boot.wim` через подписанный `wimboot`. Затем WinPE подключает полные установочные файлы по SMB. Проверка останавливается до записи на диск.

## Источники и файлы

- ISO: `19045.6280.250817-2324.22H2_RELEASE_SVC_PROD3_CLIENTPRO_OEMRET_X64FRE_RU-RU.ISO` в подключённой SMB-папке `//192.168.10.10/Downloads/iso`.
- `wimboot` 2.9.0: `https://github.com/ipxe/wimboot/releases/download/v2.9.0/wimboot`; SHA-256 `5f067ccdc4d084d5bf77b6c853bd0f8402dfc2b4cd1b103d358993ae97fae8e3`.
- `sources/boot.wim` этого ISO: 597 191 021 байт; SHA-256 `8401543d872d0feb851efa2faf87a6d45e472db6b1e3c65d144af2cbd8df0de4`.

Сервер хранит эти два файла в `/srv/pxe/tftp/windows/wimboot` и `/srv/pxe/tftp/windows10/boot.wim`. Он не публикует SMB-шару целиком. Сверка `cmp` подтвердила, что копия WIM равна файлу внутри ISO. `sbverify --list` на Ubuntu показал подписи wimboot от цепочек Microsoft Corporation UEFI CA 2011 и Microsoft UEFI CA 2023. Наличие подписи не заменяет отдельный запуск клиента с Secure Boot.

## Публикация и проверка

В админке **Меню** отметить **Windows 10 x64 — запуск WinPE** и оставить включённым Ubuntu, если он нужен. Нажать **Опубликовать**. Прежняя версия меню остаётся доступной для отката.

На тестовой PXE-ВМ 112 с 16 ГБ ОЗУ сначала загрузить Windows 10 в OVMF с Secure Boot выключенным. Проверить, что среда WinPE/окно установщика открылась; если установщик попросит файлы с носителя, записать это как ожидаемую границу текущего этапа. Не выбирать диск и не запускать установку. После успешного запуска повторить с Secure Boot включённым, а затем с SeaBIOS.

Пользователь подтвердил: в OVMF окно установки Windows 10 появилось и с выключенным, и с включённым Secure Boot. Первоначально `ipconfig` внутри WinPE не показал адаптер ни при VirtIO, ни при Intel E1000. После `wpeutil InitializeNetwork` E1000 появился и получил адрес из PXE-сети. Это подтверждает необходимость явной инициализации сети в данном сценарии; наличие драйвера VirtIO NIC в WIM ещё не проверено. Позднее профиль Windows 10 проверен и в SeaBIOS: установщик открылся и показал 64-ГБ SATA-диск ВМ 112. Доступ к полным установочным файлам и диску проверен ниже; успешная установка ОС не проверялась.

## Установочные файлы по SMB

На тестовом сервере содержимое того же ISO скопировано из подключения только для чтения в `/srv/pxe/installers/windows10` (905 файлов, 6,9 ГиБ). Его публикует Samba по `\\10.30.0.10\windows10`. Конфигурация хранится в [`deploy/samba/smb.conf`](../deploy/samba/smb.conf): TCP 445 только на `lo` и `ens19`, вход только из `10.30.0.0/24`, обязательная подпись SMB, чтение без записи, доступ только для отдельной учётной записи `pxe-install`. Пароль Synology не используется и не передаётся клиенту.

Пароль `pxe-install` сгенерирован на сервере и хранится только в `/etc/pxe-platform/winpe-smb-password` с правами `0600`. Пользователь может посмотреть его через SSH с `sudo -n cat`; публиковать пароль в документации или загрузочном меню нельзя. В WinPE после `wpeutil InitializeNetwork` выполнить `net use Z: \\10.30.0.10\windows10 /user:pxe-install *` и ввести пароль по запросу. Проверить `dir Z:\sources\install.wim`. После успешного чтения можно запустить `Z:\setup.exe` и остановиться до выбора диска.

На сервере `testparm -s` принял конфигурацию. `smbd` слушает `127.0.0.1:445` и `10.30.0.10:445`, но не адрес управления `192.168.10.135`. `smbclient` с учётной записью прочитал `setup.exe` и `sources/install.wim` (6 438 122 734 байта); создание каталога было отклонено с `NT_STATUS_ACCESS_DENIED`, как и подключение к шаре без учётной записи. Пользователь подключил шару из WinPE и увидел `Z:\sources\install.wim`.

Первый запуск `Z:\setup.exe` вернул «Отказано в доступе»: скопированные с ISO файлы имели Unix-права `0644`, а Samba проверяет право выполнения при запуске файла клиентом. После установки `0755` на `setup.exe` пользователь подтвердил, что установщик открылся. На все исполняемые файлы Windows в локальной копии (`.exe`, `.dll`, `.sys`, `.com`, `.ocx`, `.cpl`, `.drv`, `.efi`) затем установлено `0755` — 212 файлов. `install.wim` остался `0644`, а попытка записи через SMB после исправления по-прежнему отклоняется. Установщик дошёл до выбора диска, но не увидел 32-ГБ диск ВМ 112 с контроллером VirtIO SCSI.

## Драйвер диска для тестовой ВМ

Для Windows 10 x64 из образа virtio-win 0.1.271 взяты только `vioscsi.inf`, `vioscsi.cat` и `vioscsi.sys` (`vioscsi/w10/amd64`). Они лежат в сетевой папке `Z:\drivers\vioscsi\w10\amd64`. SHA-256 исходного ISO: `bbe6166ad86a490caefad438fef8aa494926cb0a1b37fa1212925cfd81656429`. [Проект virtio-win](https://github.com/virtio-win/kvm-guest-drivers-windows/wiki/Driver-installation) описывает загрузку драйвера на экране выбора диска. ISO скачан с зеркала [архивного выпуска](https://fedora-virt.repo.nfrance.com/virtio-win/direct-downloads/archive-virtio/virtio-win-0.1.271-1/); его хеш совпал с [зафиксированным хешем этого выпуска](https://github.com/virtio-win/virtio-win-pkg-scripts/issues/121).

На сервере проверено чтение всех трёх файлов через SMB с учётной записью `pxe-install` и побайтовое совпадение с локальными копиями. В WinPE файлы также видны на `Z:`. Команда `drvload Z:\drivers\vioscsi\w10\amd64\vioscsi.inf` вернула `0x80070103`, поэтому установка этого драйвера не подтверждена. В списке проблемных устройств был `PCI\VEN_1AF4&DEV_1002` — это VirtIO Balloon, а INF для VirtIO SCSI содержит `DEV_1004` и `DEV_1048`. После `diskpart` → `rescan` → `list disk` пользователь увидел **Диск 0, 32 ГБ, 32 ГБ свободно**. Значит, диск доступен текущему WinPE; его появление нельзя приписывать попытке `drvload` без дополнительной проверки. Диск не очищать и установку не продолжать.

Проверка серверных файлов: `HEAD` вернул HTTP 200 и размеры 76 064 байта для `wimboot` и 597 191 021 байт для `boot.wim`. Запрос диапазона первых 1024 байт WIM вернул HTTP 206 и ровно 1024 байта. После замены Control все пять служб остались активны, HTTPS-страница входа ответила HTTP 200, SHA-256 действующего меню до и после замены остался `2777c5df23b82398483177bb8dc73999dd1bdc052f2601642682698bbb6d30f6`. До ручной публикации пункт Windows 10 в действующем меню отсутствует.

## Откат

Если профиль не загрузится, вернуть прежнюю версию через **Меню → Версии**. Прежний бинарный файл Control лежит в `/var/backups/pxe-platform-pre-winpe-20261016/pxe-control`. Восстановить его в `/usr/local/bin/pxe-control` и перезапустить только `pxe-control`; Boot, proxy-DHCP и текущий опубликованный снимок меню работают независимо от панели. Файлы Windows 10 в `/srv/pxe/tftp` можно удалить после исключения пункта из меню.

Для отката SMB остановить и выключить `smbd.service`, затем убрать `/srv/pxe/installers/windows10` после завершения клиентских проверок. `nmbd.service` остаётся замаскированным: для доступа по IP достаточно TCP 445. Эти действия не меняют PXE-меню и DHCP.

## Следующий шаг

Следующая проверка — Windows 11 x64. Для неё использовать тот же закреплённый выпуск wimboot, который поддерживает извлечение `boot.stl` из новых WIM. Наличие диска в Windows 10 WinPE подтверждено командой DiskPart; установка ОС на диск не выполнялась.
