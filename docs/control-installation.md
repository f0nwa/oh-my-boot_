# Control и HTTPS-админка OMB

Актуальное руководство для OMB. Адрес существующего стенда: **https://192.168.10.135:8443**. Команды первой установки ниже предназначены для нового сервера; на работающем стенде повторно создавать пользователей, базы, сертификат и конфигурацию не нужно.

[English version](en/control-installation.md). Отчёты выкаток и инструкции прежних версий сохранены в [истории проекта](project-history.md). Результат технического переименования — в [отчёте миграции](research/2026-10-31-omb-technical-migration.md).

## Службы и пути

`omb-control` обслуживает HTTPS, пользователей, роли, установки, черновик и версии меню. Он работает от системного пользователя `omb-control` и обращается к PostgreSQL через одноимённую роль с локальной peer-аутентификацией.

| Назначение | Текущее имя или путь |
| --- | --- |
| Процесс и служба | `/usr/local/bin/omb-control`, `omb-control.service` |
| Административная команда | `/usr/local/bin/omb-controlctl` |
| База | `omb_control` |
| Настройки запуска | `/etc/omb/control.env` |
| Сертификат и ключ | `/var/lib/omb-control/control.crt`, `control.key` |
| API Boot | `/run/omb-boot/control.sock` |
| API Agent | `/run/omb/agent.sock` |
| API Images | `/run/omb-images/images.sock` |
| Снимок опубликованного меню | `/var/lib/omb-boot/menu.ipxe` |

Boot отдаёт меню клиентам на `http://10.30.0.10:8080/boot/menu.ipxe`. Agent управляет загрузочной сетью и монтированиями, Images — каталогом ISO. Остановка Control не останавливает эти службы и не заменяет опубликованное меню.

## Первая установка Control

Сначала подготовьте Boot и Agent по [руководству сервера](installation.md), установите Images по [руководству хранилищ](images-installation.md) и запустите PostgreSQL. Группа `omb-images` должна существовать: она указана в `SupplementaryGroups` юнита Control. В примерах загрузочный интерфейс — `ens19`, управляющий адрес — `192.168.10.135`; для другого сервера замените их своими значениями.

Сборка выполняется в корне репозитория:

~~~sh
mkdir -p dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o dist/omb-control ./cmd/omb-control
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o dist/omb-controlctl ./cmd/omb-controlctl
~~~

Если сборка выполнена на другой машине, перенесите каталоги `dist` и `deploy` на сервер. Следующие серверные команды выполняются из корня каталога с этими файлами, в Bash под root. Они относятся только к первой установке:

~~~sh
install -m 0755 dist/omb-control dist/omb-controlctl /usr/local/bin/
useradd --system --user-group --home-dir /var/lib/omb-control --shell /usr/sbin/nologin omb-control
install -d -m 0700 -o omb-control -g omb-control /var/lib/omb-control
install -d -m 0750 -o root -g root /etc/omb

runuser -u postgres -- psql -v ON_ERROR_STOP=1 -c 'CREATE ROLE "omb-control" LOGIN'
runuser -u postgres -- createdb --owner=omb-control omb_control
runuser -u omb-control -- psql -v ON_ERROR_STOP=1 --dbname=omb_control < deploy/sql/control.sql
~~~

На существующем стенде сохраняйте полную схему и данные, включая дополнительные таблицы. Не заменяйте рабочую базу пустой схемой.

### TLS

Для лабораторного сервера можно создать самоподписанный сертификат с управляющим IP в SAN. Этот блок откажется перезаписывать уже существующий сертификат или ключ:

~~~sh
(
  set -eu
  umask 077
  test ! -e /var/lib/omb-control/control.crt
  test ! -e /var/lib/omb-control/control.key
  openssl req -x509 -newkey rsa:3072 -sha256 -nodes -days 90 \
    -subj '/CN=omb-control' \
    -addext 'subjectAltName=IP:192.168.10.135' \
    -keyout /var/lib/omb-control/control.key \
    -out /var/lib/omb-control/control.crt
  chown omb-control:omb-control /var/lib/omb-control/control.crt /var/lib/omb-control/control.key
  chmod 0600 /var/lib/omb-control/control.key
  chmod 0644 /var/lib/omb-control/control.crt
)
~~~

Если используется сертификат вашей инфраструктуры, установите его и соответствующий ключ по тем же путям. Сертификат должен включать адрес или имя, по которому открывают панель. Для самоподписанного сертификата потребуется доверие в браузере.

### Настройки и запуск

Создайте `/etc/omb/control.env` при первой установке. Проверка в начале блока защищает уже существующий файл от перезаписи:

~~~sh
(
  set -eu
  test ! -e /etc/omb/control.env
  cat > /etc/omb/control.env <<'ENV'
OMB_CONTROL_LISTEN=192.168.10.135:8443
OMB_CONTROL_INTERFACES=ens19
OMB_CONTROL_DATABASE_URL="host=/var/run/postgresql dbname=omb_control user=omb-control"
OMB_CONTROL_BOOT_BASE_URL=http://10.30.0.10:8080
ENV
  chmod 0640 /etc/omb/control.env
)
install -m 0644 deploy/systemd/omb-control.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now omb-control.service
~~~

Порт панели привязан к управляющему адресу; в список разрешённых для настройки интерфейсов входит только загрузочный интерфейс. При запуске Control режим DHCP и настройки внешнего DHCP-сервера не меняются.

## Первый администратор и восстановление доступа

Пароля по умолчанию нет. `create-admin` создаёт первого администратора только в пустой таблице пользователей. Следующий блок выполняется под root в Bash; замените `admin` выбранным именем. Пароль вводится без отображения и передаётся команде через stdin:

~~~sh
set +x
set -a
. /etc/omb/control.env
set +a
read -r -s -p 'Новый пароль: ' omb_admin_password
printf '\n'
printf '%s\n' "$omb_admin_password" |
  runuser -u omb-control -- env OMB_CONTROL_DATABASE_URL="$OMB_CONTROL_DATABASE_URL" \
  /usr/local/bin/omb-controlctl create-admin -username admin
unset omb_admin_password
~~~

Для сброса пароля существующего пользователя используйте этот блок, заменив `admin` его именем:

~~~sh
set +x
set -a
. /etc/omb/control.env
set +a
read -r -s -p 'Новый пароль: ' omb_admin_password
printf '\n'
printf '%s\n' "$omb_admin_password" |
  runuser -u omb-control -- env OMB_CONTROL_DATABASE_URL="$OMB_CONTROL_DATABASE_URL" \
  /usr/local/bin/omb-controlctl reset-password -username admin
unset omb_admin_password
~~~

Сброс завершает прежние сеансы этого пользователя. Роли: `admin`, `operator`, `observer`. Язык RU/EN и тема выбираются в личном кабинете. После смены технических имён требуется новый вход; сохранённые пароли пользователей остаются прежними.

## Установки и меню

В «Библиотеке» подготовьте загрузочный профиль, файлы ответов и нужные драйверы. На странице «Установки» создайте отдельные варианты Windows или Ubuntu; несколько установок могут использовать один профиль.

На странице «Меню» выберите установки, названия и папки. Черновик не виден клиентам до публикации. При публикации Control проверяет зависимости, создаёт версию и передаёт согласованный снимок Boot. Сохранение черновика само по себе не меняет клиентское меню.

Возврат версии через «Меню → Версии» также проверяет доступность зависимостей. Если ISO, профиль или подготовленные файлы недоступны, прежнее действующее меню сохраняется. Возврат меню не восстанавливает удалённые ISO или данные на NAS.

## Каталог драйверов WinPE

В «Библиотека → Драйверы» импортируются папки с INF и сопутствующими файлами либо ZIP той же структуры. При создании установки выбираются конкретные INF. Производный WIM с драйверами используется этой установкой; исходный ISO остаётся на хранилище.

Файлы ответа находятся в «Библиотека → Файлы ответов». Windows XML привязан к профилю. Публикуйте вариант только после успешной подготовки и проверки его файлов. Удаление используемого профиля или зависимости блокируется связями.

## Ubuntu Autoinstall

В «Библиотека → Файлы ответов», в блоке Ubuntu Autoinstall, выберите «Создать файл Ubuntu». Та же команда доступна при создании установки Ubuntu. Редактор рассчитан на Ubuntu Desktop и содержит восемь разделов: файл и источник, язык и регион, пользователь, диск, оборудование, программы и репозиторий, сеть и SSH, завершение установки.

Список дополнительных пакетов принимает имена пакетов и отклоняет суффикс удаления `-`; имена вроде `g++` допустимы.

Можно задать полное имя пользователя, до четырёх раскладок с вариантами и переключением, набор приложений из подготовленного ISO, установку сторонних драйверов и кодеков, до 128 APT-пакетов, зеркало Ubuntu, статический IPv4 по точному MAC, SSH-сервер с публичными ключами и скрипт до 16 КиБ. По умолчанию используются DHCP, отключённый SSH и ручная разметка. Автоматическая разметка очищает диск только по точному серийному номеру; неизвестный номер не заменяется первым доступным диском.

Слева переключаются разделы, справа доступны сводка «Что получится», точный YAML и «Проверка». Основной сценарий работает без JavaScript. При включённом JavaScript предпросмотр обновляется после изменения полей, а сохранение доступно только после актуальной проверки. Пароль нужен при первом предпросмотре, после истечения 10 минут и для новой копии; действительный предпросмотр позволяет менять настройки и сохранять без повторного ввода. Открытый пароль не возвращается страницей и не записывается в библиотеку.

Доступные наборы приложений берутся из того же ISO, который отдаёт Boot. Подготовьте метаданные по [руководству Ubuntu](ubuntu-desktop-pxe.md#подготовка-источника). Без них доступен только вариант «Как в ISO». Если явно выбранный набор стал недоступен, сохранение или публикация отклоняется. Сохранённые файлы не переписываются при смене ISO.

Дополнительные пакеты, SSH-сервер, драйверы и кодеки требуют доступного клиенту репозитория Ubuntu. Можно задать локальное HTTP(S)-зеркало, которое содержит и основной архив, и security-пакеты. Режим «Без обращения к архивам пакетов» отключает поиск зеркала и обновление установщика и исключает перечисленные дополнительные компоненты. Пользовательский скрипт при этом может самостоятельно обращаться к сети. Статический адрес применяется установщиком после получения ответов; начальная PXE-загрузка продолжает использовать DHCP.

Скрипт выполняется от root внутри установленной системы через `/bin/sh -eu` до перезагрузки; ненулевой код завершения останавливает установку. Это не сценарий первого входа в графический рабочий стол. После установки можно перезагрузить или выключить компьютер.

Сохранённый файл неизменяем: для нового варианта создаётся копия. Выберите проверенный файл в установке и опубликуйте её через черновик меню. Без файла ответов установка остаётся ручной. Boot выдаёт согласованную пару NoCloud `user-data` и `meta-data` из `/assets/ubuntu-autoinstall/…`. Метка «Проверен конструктором» подтверждает проверку структуры и параметров; успешная установка, вход в рабочий стол, драйверы и Secure Boot проверяются на клиенте отдельно.

## Доступность хранилищ и восстановление

На странице «Система → Хранилища» видны состояние и ошибка хранилища. Images проверяет доступность в фоне; ошибка не стирает прежний каталог. Публикация установки с недоступным источником отклоняется.

Agent восстанавливает собственные SMB-монтирования, затем ISO-профили. Настройка автоматического восстановления и ручной запуск находятся на странице хранилищ. На существующем стенде восстановление включено с интервалом 300 секунд. Ограничения записи на внешнем NAS определяются его учётной записью и правами.

## Диагностика и откат

Команды выполняются под root:

~~~sh
systemctl status omb-control.service omb-boot.service omb-agent.service omb-images.service omb-dnsmasq.service
journalctl -u omb-control.service -u omb-boot.service -u omb-agent.service -n 100 --no-pager
runuser -u omb-control -- psql -XAt --dbname=omb_control -c 'SELECT 1'
curl --fail --cacert /var/lib/omb-control/control.crt https://192.168.10.135:8443/login
curl --fail http://10.30.0.10:8080/boot/menu.ipxe
~~~

Если нужно остановить только неисправную панель, используйте `systemctl stop omb-control.service`. Boot, Agent, Images и DHCP продолжат работать. Для запуска панели — `systemctl start omb-control.service`. Сгенерированный `/etc/omb/dnsmasq.conf` не редактируется ради исправления Control.

Перед обновлением сохраните конфигурацию, TLS-файлы, бинарные файлы, юниты и нужные базы. Если обновление меняет общие форматы или связи, нужна согласованная копия всех затронутых баз и файлов при остановленных писателях. Для отката выбирайте комплект и схему одной совместимой версии; замены одного бинарного файла может быть недостаточно.

Откат именно технической миграции описан в [отдельной процедуре](recovery.md). Она восстанавливает состояние на момент сохранённой копии; прежде нужно сохранить более новые данные и выделить окно обслуживания. Проверенная копия перехода на существующем стенде находится в `/root/omb-migration-20261031/backup`.

## Границы проверки

Сервер прошёл проверку восстановления файлов и баз, пересборку WinPE, TFTP, SMB/NAS и перезагрузку. Пользователь подтвердил загрузку UEFI Secure Boot с XML и драйверами. Полный повторный клиентский прогон отложен до завершения основной разработки; подробности — в [отчёте миграции](research/2026-10-31-omb-technical-migration.md).

Исторические даты, прежние команды отката и контрольные суммы выкаток находятся в [истории проекта](project-history.md).
