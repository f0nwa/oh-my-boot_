OMB спроектирован для серверов без доступа в интернет. Каждый выпуск поставляется как самодостаточный подписанный локальный APT-репозиторий с пакетом `omb`, системными зависимостями и кумулятивными SQL-миграциями, проверяется до применения и умеет автоматически откатываться при любом сбое.

## Каналы обновлений: `stable` и `dev`

| Канал | Ветка Git | Тег выпуска | Версия пакета `.deb` | Отображение в панели |
| --- | --- | --- | --- | --- |
| **`stable`** | `main` | `vX.Y.Z` | `X.Y.Z` | Тихая шапка, версия и канал видны в карточке «Выпуск OMB» на `/system` |
| **`dev`** | `dev` | `vX.Y.Z-dev.N` | `X.Y.Z~dev.N` | Янтарный бейдж `dev` рядом с логотипом в шапке + карточка на `/system` |

Текущий канал сервера хранится в `/var/lib/omb-deployment/CHANNEL`, а метаданные пакета — в `/usr/share/omb/release.json` (`channel`, `commit`, `display_version`, `package`, `version`). Случайная смена канала при обновлении заблокирована и требует явного флага `--allow-channel-switch`.

## Самодостаточный APT-репозиторий и `current.deb`

На машине сборки команда `scripts/offline-deb.py build` формирует самодостаточный каталог `apt-repo`:

- единый пакет `omb_<версия>_amd64.deb` (бинарники в `/usr/bin/`, юниты systemd в `/usr/lib/systemd/system/`, помощники в `/usr/lib/omb/`, начальные схемы `/usr/share/omb/bootstrap/`, кумулятивные миграции `/usr/share/omb/migrations/manifest.json` и встроенная Wiki);
- локальный индекс `Packages.gz` и все транзитивные системные `.deb`-зависимости целевой Ubuntu;
- файл `repo-manifest.json` (формат `2`) с контрольными суммами всех артефактов, системных пакетов, загрузочных файлов (`iPXE`, `shim`, `wimboot`), модулей `go.mod` и закреплённого upstream конструктора `unattend`;
- криптографическая подпись `repo-manifest.sig` (OpenSSL SHA-256).

На самом сервере в `/var/lib/omb-deployment/current.deb` сохраняется копия текущего установленного пакета `omb` (вместе с `PACKAGE`, `PACKAGE_SHA256`, `CHANNEL`, `COMMIT`). Благодаря этому при обновлении не нужны прежний установочный архив или ручная передача версий и хешей — достаточно нового `apt-repo` и публичного ключа.

## Реестр `schema_migrations` и прыжки через версии

Каждая из трёх баз (`omb_boot`, `omb_images`, `omb_control`) ведёт таблицу `schema_migrations (id, sha256, applied_at)`. Миграции внутри пакета нумеруются последовательно (`NNNN_name.sql`) и перечисляются в `/usr/share/omb/migrations/manifest.json`:

- при первичной установке (`install`) после загрузки начальной схемы в `schema_migrations` сразу фиксируются все миграции из пакета;
- при обновлении (`update`) планировщик сравнивает `manifest.json` нового пакета со строками `schema_migrations`: проверяет целостность SHA-256 уже применённых миграций (удаление или изменение старой миграции запрещено) и применяет в транзакциях только недостающие миграции в порядке `omb_boot` → `omb_images` → `omb_control`.

Поскольку каждый выпуск несёт полный накопительный набор миграций, сервер можно обновлять сразу через несколько промежуточных версий (например, с `0.2.0~dev.1` сразу на `0.2.0~dev.5`) при условии, что новая версия пакета больше установленной (`dpkg --compare-versions`).

## Установка, обновление и откат (`offline-deploy.sh`)

Основные команды на сервере OMB (рядом со скриптами `offline-deploy.sh`, `offline-install-lib.sh` и `offline-deb.py`):

```bash
# 1. Проверить подпись и целостность комплекта до установки или обновления
python3 scripts/offline-deb.py verify-repo \
  /path/to/apt-repo \
  --public-key /path/to/trusted-release-public.pem

# 2. Первичная установка на чистую Ubuntu (укажите имя PXE-интерфейса или none)
sudo bash scripts/offline-deploy.sh install \
  /path/to/apt-repo \
  /path/to/trusted-release-public.pem \
  MANAGEMENT_IP \
  none

# 3. Штатное обновление из подписанного локального репозитория
# (для явной смены канала добавьте --allow-channel-switch сразу после update)
sudo bash scripts/offline-deploy.sh update \
  /path/to/apt-repo \
  /path/to/trusted-release-public.pem \
  MANAGEMENT_IP

# 4. При необходимости откатиться на предыдущую версию
sudo bash scripts/offline-deploy.sh rollback MANAGEMENT_IP
```

Что делает `offline-deploy.sh update`:

1. Проверяет подпись `repo-manifest.sig`, контрольные суммы, целевую ОС и архитектуру, отсутствие незавершённого маркера `PENDING`, рост версии (`new_version > old_version`), совпадение канала и соответствие установленного пакета локальному кешу `/var/lib/omb-deployment/current.deb`.
2. Сравнивает `current.deb` с новым пакетом и вычисляет недостающие миграции по `schema_migrations`, автоматически определяя область изменений (`scope`): какие службы и какие из трёх баз затронуты. Незатронутые службы не перезапускаются.
3. Проверяет запас места, создаёт полную резервную копию в `/var/backups/omb/offline.<id>` (предыдущий `omb.deb`, конфиги, снимки и проверенные восстановлением дампы затронутых БД) и выставляет маркер `PENDING`.
4. Устанавливает новый `.deb`, применяет недостающие SQL-миграции с записью в `schema_migrations`, проверяет сохранность учётных записей, активность служб, ответ HTTPS и неизменность меню `omb-boot`. Каталоги `/srv/omb/tftp` и `/etc/omb` не перезаписываются.
5. Обновляет `/var/lib/omb-deployment/current.deb` и маркеры состояния; если любой шаг завершился ошибкой (или процесс оборвали по `SIGKILL`), выполняется автоматический или ручной `rollback`: восстанавливаются прежний `.deb` и базы, а мигрированные базы сохраняются под именами `omb_retained_<id>` с отключёнными подключениями для разбора причины.

## Консольное управление и онлайн-обновление (`omb`)

Для серверов с доступом в интернет и повседневной диагностики доступна единая консольная утилита `omb`:

```bash
# Проверить установленную версию, канал, режим установки и состояние всех 7 служб
sudo omb status

# Показать текущий канал выпусков или переключить его (stable или dev)
sudo omb channel [stable|dev]

# Обновить сервер по сети из GitHub Releases (SHA-256, резервная копия БД, миграции)
sudo omb update

# Обновить сервер без интернета из локального .deb (+ SHA256SUMS в той же папке)
sudo omb update --deb ./omb_<версия>_amd64.deb
```

Для изолированных серверов с полной криптографической проверкой подписи репозитория и автоматическим откатом используйте подписанный локальный APT-репозиторий и `offline-deploy.sh` выше (`sudo omb status`, `sudo omb channel` и `sudo omb update --deb` работают без доступа к интернету).

## Проверка целостности и системное время (NTP)

После обновления или при диагностике проверьте целостность установленных файлов пакета:

```bash
dpkg --verify omb
```

Чистый вывод означает, что все файлы пакета на месте и не повреждены.

Системное время и часовой пояс настраиваются в карточке **«Время сервера»** на [Система → Обзор](/system) (кнопка «Изменить…»):

- режим **Корпоративный NTP** — `omb-agent` автоматически определяет активный демон (`chrony` или `systemd-timesyncd`), записывает серверы времени в `/etc/chrony/sources.d/omb.sources` или `/etc/systemd/timesyncd.conf.d/omb.conf` и применяет конфигурацию;
- режим **Вручную** — задаёт точные дату, время и часовой пояс для полностью изолированных стендов без NTP.

## Аварийное восстановление

- **Неудачная правка меню:** откройте [Меню](/menu) → «История версий» → «Откатить».
- **Ошибка в параметрах PXE-сети:** `omb-agent` проверяет `dnsmasq.conf` через `dnsmasq --test` и откатывает конфиг автоматически при ошибке.
- **Сбой после обновления пакета:** выполните `sudo bash scripts/offline-deploy.sh rollback MANAGEMENT_IP` — скрипт восстановит предыдущую версию `.deb`, канал и согласованные дампы БД из `/var/backups/omb/`.
- **Ручное резервное копирование:** сохраняйте `/etc/omb/` (включая `secrets.key`), `/var/lib/omb-control/` (TLS) и согласованные дампы `pg_dump` баз `omb_control`, `omb_images` и `omb_boot` при остановленных службах-писателях.
