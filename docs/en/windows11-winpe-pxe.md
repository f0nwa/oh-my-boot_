> On 20.10.2026 this static item, the local ISO copy, the `windows11` and `windows11iso` shares and the `pxe-windows11-iso` service were removed; Windows 11 boots through ISO profiles (see the [Images guide](images-installation.md)). The history of the first check follows.

The ISO `26100.5067.250818-2008.GE_RELEASE_SVC_PROD3_CLIENTPRO_OEMRET_X64FRE_RU-RU.ISO` was found in the connected SMB folder. For the initial boot, `sources/boot.wim` was copied from it to `/srv/pxe/tftp/windows11/boot.wim`. Size: 698,729,786 bytes, SHA-256 `33f30dccd7479ddb31fc6cd692ca7f420eaee5af388f8ecc8fa3f9524a31d4a4`; `cmp` confirmed that it matches the file in the ISO. Boot serves it at `/assets/windows11/boot.wim`: HTTP HEAD 200, a request for the first 1024 bytes returns 206. The boot uses the already pinned and checked `wimboot` 2.9.0 from the [Windows 10 profile](windows-winpe-pxe.md).

The admin interface offers a separate **Windows 11 x64 — start WinPE** item. It is published manually on the **Menu** page, keeping the selected Ubuntu and Windows 10 items. Replacing the Control binary does not change the active published menu; its SHA-256 before and after the replacement stayed `c3730b5ceed31bc218b7ab9cd42c1f3fc6e4d944e739117a85b2ff6a8d2f676c`. The previous binary is kept in `/var/backups/pxe-platform-pre-win11-20261016/pxe-control`.

The user published the Windows 11 item; the active menu contains Ubuntu, Windows 10 and Windows 11 (SHA-256 `7120f842b72b1f2dda998c79f1c9385c21c1461f7eacb7f82d96d5ec51729b89`). On VM 112 in OVMF the Windows 11 installation window appeared with Secure Boot both disabled and enabled. The installation to disk was not started.

## Full installation files

The ISO content was copied from the read-only connection to `/srv/pxe/installers/windows11` (1054 files). A `cmp` comparison confirmed that `sources/boot.wim` and `sources/install.wim` match the ISO; `install.wim` is 8,693,893,898 bytes. A separate `\\10.30.0.10\windows11` share is defined in [`deploy/samba/smb.conf`](../../deploy/samba/smb.conf) with the same restrictions as Windows 10: only `10.30.0.0/24`, the `pxe-install` account, mandatory SMB signing and read-only access. The password is the same as for Windows 10; the source storage password is not sent to the client.

On the server, `testparm` accepted the new configuration. `smbclient` as `pxe-install` read `setup.exe` byte for byte and saw `install.wim`, but could not create a directory; anonymous access was rejected. The Windows 10 share stayed available after the change. In WinPE with Secure Boot enabled, the user ran `wpeutil InitializeNetwork`, connected `\\10.30.0.10\windows11` and confirmed that `Z:\sources\install.wim` is visible.

Right after `Z:\setup.exe` started, the installer asked for a driver to detect hardware. In this Windows 11 WinPE, `diskpart` → `rescan` → `list disk` **did not show** the 32 GB disk of VM 112, connected as `scsi0` on VirtIO SCSI single. The user shut down the VM, detached the disk without deleting its image and attached the same image as `sata0`. After a new WinPE boot and `rescan`, `list disk` showed the disk. This confirms a problem detecting the disk on VirtIO SCSI in the current Windows 11 WinPE. [Proxmox describes this way of changing the bus](https://pve.proxmox.com/wiki/Migrate_to_Proxmox_VE). The disk was enlarged to 64 GB, which matches the [Windows 11 minimum](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements), but the driver request remained.

The detailed log `X:\$WINDOWS.~BT\Sources\Panther\setupact.log` gave the exact cause of the current screen: `Driver: Found install image at [(null)]`, `Found Media path at [(null)]`, `Unable to find media`. In the same log Setup sees a `QEMU HARDDISK` of 68,719,476,736 bytes on the `Serial ATA` bus. So the driver message here refers to the missing **installation source**, not to detecting the SATA disk. The automatic Setup starts before `Z:` is connected manually. The server has an executable `sources/setup.exe`, which [Microsoft recommends for starting from WinPE](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/windows-setup-supported-platforms-and-cross-platform-deployments?view=windows-11); trying to start it while Setup is already open returns to the command prompt at once. `setuperr.log` also contains MOUPG errors `0x80072EE7`, `0x80070490` and `0x80070002`, but the log does not link them to the driver request screen. The disk was not cleaned and the installation was not started.

To roll back, disable `smbd.service`, restore `/var/backups/pxe-platform-pre-win11-smb-20261016/smb.conf` to `/etc/samba/smb.conf` and start `smbd.service`. The rollback does not affect the old Windows 10 folder. Delete the full copy in `/srv/pxe/installers/windows11` only after the client checks are finished.

## Automatic start from the source ISO: lab check on 16.10.2026

A first version of starting Windows 11 without commands in WinPE was prepared. The source ISO stays on the connected Synology SMB share and is mounted on the PXE server as read-only UDF in `/mnt/pxe-platform-iso/windows11`. A new Samba share, `\\10.30.0.10\windows11iso`, serves the files straight from this mount; no full copy of the ISO was made for the new path. The old local copy `/srv/pxe/installers/windows11` is kept for rollback for now.

A separate `pxe-iso` user has read-only access to the new share. Its password is stored in `/etc/pxe-platform/pxe-iso-password` with mode `0600`; these are separate credentials, not the Synology password and not the earlier `pxe-install`. The server inserts this password into `pxe-setup.cmd`, which is sent to the PXE client at boot. So a machine inside the isolated `10.30.0.0/24` network can get the password of the read-only share. Boot returns HTTP 404 for this file when it is requested from the management network. Anonymous Samba access is rejected; creating a directory with the `pxe-iso` account returned `NT_STATUS_ACCESS_DENIED`.

`wimboot` also loads `winpeshl.ini` and `pxe-setup.cmd` before `boot.wim`. In WinPE the script runs `wpeinit`, waits for the network, connects `windows11iso`, checks `sources/install.wim` and starts `sources/setup.exe /InstallFrom:Y:\sources\install.wim`. If the source is unavailable, a command prompt with a message remains. The script is kept in the repository as a template without the password; the server creates the working file when `pxe-windows11-iso.service` starts.

Checked on the server: `boot.wim` matches the file inside the mounted ISO byte for byte; HTTP returns 200 for `wimboot`, `winpeshl.ini` and `boot.wim`; all PXE services, Samba and the mount are active; the HTTPS admin interface responds. The user published the menu again; the active script contains both new `initrd` lines. A new empty VM 113 in OVMF with Secure Boot disabled booted over PXE to the initial Windows 11 setup screen. On the server, `smbstatus` showed its connection from `10.30.0.19` to `windows11iso` as `pxe-iso`, so the automatic connection to the source ISO worked. After the initial screen, Setup stopped with a message that the PC is not compatible with Windows 11. The VM has 16 GB of memory, four virtual CPUs, a 70 GB SATA disk and OVMF, but its original configuration had no `TPM State`; the user then added TPM 2.0. The first run did not reach the disk selection screen, and nothing was written to disk.

After TPM 2.0 was added, the first automatic attempt to connect the ISO failed with Windows error 53 (“The network path was not found”). In the same WinPE session the address `10.30.0.19` had already been obtained and the server answered ping, and running `pxe-setup.cmd` again manually connected the ISO and let Setup proceed to the disk list. This points to SMB becoming ready later than `wpeutil WaitForNetwork`, not to a missing file or disk driver. The script was extended with 12 `net use` attempts with a short pause between them. The updated file was deployed on the server without restarting Samba or changing the published menu. On the next full PXE boot the VM connected to `windows11iso` by itself and read `sources/setup.exe` and `sources/install.wim`; the installer opened without commands in WinPE. The user went through the wizard screens manually to the disk list without errors. No disk was selected and the installation was not started. Going through the wizard screens automatically belongs to the future `autounattend.xml` profiles.

The first test with Secure Boot enabled showed SMB becoming ready even later: 12 attempts ended with Windows error 2, although WinPE had `10.30.0.19` and the server answered ping. Running the script again manually in the same WinPE session opened the installer; the server saw a new SMB session and a read of `sources/setup.exe`. For the next check the number of attempts was increased to 45 (about a minute and a half), and the last attempt shows the original Windows error text. The renderer was checked on the real template, and the updated file was deployed on the server. After a full restart of VM 113 with Secure Boot enabled, the installer opened without manual commands; the console window closed. The user went through the wizard screens manually to the disk list and confirmed that the 70 GB disk is visible. In this boot the server recorded reads of `sources/setup.exe` and `sources/install.wim` from the mounted ISO. In this successful run the SMB wait delay was not needed; the check confirms the automatic start with Secure Boot, but not the maximum wait time during a repeated network failure. The Legacy BIOS check remained a separate task for Windows 10.

To roll back the automatic start, restore the previous version on the **Menu** page. If needed, restore the binaries `/usr/local/bin/pxe-control.pre-win11-auto-20261016` and `/usr/local/bin/pxe-boot.pre-win11-auto-20261016`, then restart the matching services. The separate Samba share can be removed by restoring `/etc/samba/smb.conf.pre-windows11iso-20261016`; after `pxe-windows11-iso.service` is stopped, the source ISO stays on Synology.
