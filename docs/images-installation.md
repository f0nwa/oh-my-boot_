# Каталог ISO на тестовой ВМ

> Актуальные команды установки используют целевые имена OMB. Датированные отчёты о развёртывании, исходные пути резервных копий и результаты относятся к стенду до миграции; его перенос ещё предстоит. См. [план технической миграции](../docs/superpowers/plans/2026-10-31-omb-technical-migration.md).

[English version](en/images-installation.md)

Этот шаг добавляет сервис Images и список найденных ISO в существующую HTTPS-админку. Он не меняет работу DHCP, Boot и опубликованное PXE-меню. Найденный ISO имеет состояние «Обнаружен, не проверен» и пока не загружается по сети.

## Настройка

Собрать `./cmd/omb-images`, `./cmd/omb-imagesctl` и обновлённый `./cmd/omb-control` для Linux amd64. Создать системного пользователя и группу `omb-images`, PostgreSQL-роль и отдельную базу `omb_images`. Применить [схему Images](../deploy/sql/images.sql) от имени владельца базы. Установить [юнит Images](../deploy/systemd/omb-images.service) и обновить [юнит Control](../deploy/systemd/omb-control.service), чтобы Control получил доступ к Unix-сокету Images. Для Images нужна переменная:

```ini
OMB_IMAGES_DATABASE_URL=host=/var/run/postgresql dbname=omb_images user=omb-images
```

Сервис Images открывает только `/run/omb-images/images.sock`. Внешний TCP-порт ему не нужен. Для пустого местного хранилища можно создать `/var/lib/omb-images/iso` с правом чтения для `omb-images`, затем зарегистрировать его от имени этого пользователя:

```sh
sudo -u omb-images env OMB_IMAGES_DATABASE_URL='host=/var/run/postgresql dbname=omb_images user=omb-images' \
  /usr/local/bin/omb-imagesctl add-path -name Local -kind local -root /var/lib/omb-images/iso
```

Чтобы загружать ISO в местное хранилище из админки, дайте группе `omb-images` право записи в каталог (`sudo chmod 2770 /var/lib/omb-images/iso`). Unit `omb-images.service` уже разрешает запись в `/var/lib/omb-images` (`ReadWritePaths=-/var/lib/omb-images`). Пока каталог доступен только для чтения, хранилище работает как раньше, но в списке «Хранилище» при загрузке его нет, а на странице «Хранилища» у него пометка «только чтение». Профили Windows можно готовить из ISO местных хранилищ внутри `/var/lib/omb-images`: Agent монтирует ISO только из SMB-подключений и из этого каталога.

Свободное место показывается для каждого доступного хранилища (statfs корня, не дольше 3 секунд): при выборе хранилища для загрузки, на страницах «Хранилища» и «Система». Для SMB это место на общей папке NAS, для местного хранилища — на файловой системе сервера.

Другой уже смонтированный каталог регистрируется отдельной командой с новым именем и `-kind mounted`. Путь должен быть настоящей точкой монтирования без символьных ссылок в пути; Images проверяет его до регистрации, перед обходом и после обхода файлов. Если монтирование исчезло или сменилось, прежний каталог сохраняется. Управляемое SMB-подключение добавляется через админку.

На странице **Образы** администратор или оператор нажимает «Обновить». Запрос запускает сканирование в фоне и сразу возвращает страницу; состояние и найденные файлы появляются после обновления страницы. Наблюдатель видит каталог, но не может запускать сканирование. В аудит записывается принятие запроса, а итог сканирования показывается в состоянии хранилища. При ошибке чтения прежние записи сохраняются, а хранилище помечается недоступным. После перезапуска службы прерванная задача также помечается ошибкой, и сканирование можно запустить снова.

## Проверка

```sh
systemctl is-active omb-images omb-control omb-boot omb-agent omb-dnsmasq
sudo -u omb-control curl --unix-socket /run/omb-images/images.sock http://unix/catalog
curl --cacert /var/lib/omb-control/control.crt https://192.168.10.135:8443/login
curl -fsS http://10.30.0.10:8080/boot/menu.ipxe
```

## Проверка 15.10.2026

На ВМ создана база `pxe_images`, запущен сервис `pxe-images`, зарегистрирован пустой каталог `Local`. Запрос на сканирование вернул HTTP 202; после него каталог получил состояние `ready`, список ISO пуст. Доступ к Unix-сокету проверен с группой, которую использует процесс Control. Временный тест с двумя каталогами и одинаковым именем `same.iso` подтвердил раздельный учёт файлов; после удаления одного файла повторное сканирование пометило только его отсутствующим. Временные каталоги и записи удалены, остался только `Local`. HTTPS-страница входа доступна; Boot, Agent, dnsmasq, Control и Images активны. SHA-256 действующего PXE-меню до и после установки одинаков: `674ec52f0b9227bd69388dba861da5ecffb470c92da2aa7baf9607085be7c087`.

Реальный ISO пользователь предоставит позже. Веб-страница с сеансом администратора на ВМ отдельно не проверялась; HTML, экранирование имён файлов и права ролей проверены локальными тестами. Резервная копия прежнего бинарного файла и юнита Control лежит в `/var/backups/pxe-platform-pre-images/`.

После исправлений повторно установлены Images и Control. Искусственно оставленная задача в состоянии `scanning` после перезапуска Images стала `unavailable` с сообщением о прерывании; новый запрос вернул HTTP 202 и состояние `ready`. На ВМ снова работают все пять служб, страница входа отвечает HTTP 200, а SHA-256 PXE-меню остался тем же.

## Управляемые SMB-хранилища

Для этой порции нужен `cifs-utils`. Примените [миграцию Images](../deploy/sql/2026-10-15-managed-smb.sql) в базе `omb_images`, создайте `/mnt/omb-smb`, затем установите новые бинарные файлы `omb-agent`, `omb-images`, `omb-control` и [юнит Agent](../deploy/systemd/omb-agent.service). Перезагрузите systemd и перезапустите эти три службы. Boot и DHCP не меняются.

На странице **Образы** администратор указывает один прямой путь к папке ISO, например `//192.168.10.10/Downloads/iso`, пользователя и пароль. Домен можно оставить пустым. Подключение работает только для чтения. Данные нескольких подключений хранятся отдельно. Оператор может запускать повторное сканирование, наблюдатель видит каталог.

Пароль вводите только в HTTPS-форме. Админка не показывает его после сохранения. Agent хранит учётные данные в файле `/etc/omb/smb/<ключ>.cred` с правами `0600`; запись PostgreSQL содержит только адрес и путь. При неудачном подключении запись остаётся в состоянии «Недоступно»: администратор может повторить попытку с новыми учётными данными или удалить подключение. Удаление сначала отключает системное монтирование, затем удаляет запись из Images.

Найденные ISO отображаются в каталоге без публикации в PXE-меню. Если соединение пропало, прежний список файлов сохраняется, а состояние хранилища становится «Недоступно».

### Установка на тестовой ВМ, 15.10.2026

На `192.168.10.135` установлен `cifs-utils`, применена миграция базы Images, обновлены Agent, Images и Control. Старые бинарные файлы, юнит Agent и дамп базы сохранены в `/var/backups/pxe-platform-pre-managed-smb/`. Все пять служб активны. С учётной записью службы Control проверен доступ к сокетам Images и Agent; HTTPS-страница доступна с серверным сертификатом. Тестовое обращение к несуществующей SMB-шаре вернуло HTTP 503, после удаления тестового подключения Agent вернул HTTP 204; временный файл учётных данных и юнит не остались. В базе после теста осталось только прежнее локальное хранилище. SHA-256 PXE-меню не изменился: `674ec52f0b9227bd69388dba861da5ecffb470c92da2aa7baf9607085be7c087`.

После ввода учётных данных реальной шары выяснилось, что прежний параметр `prefixpath=iso` оставлял видимым корень `Downloads`; сканирование останавливалось на недоступной системной папке `#recycle`. Источник монтирования изменён на прямой путь `//192.168.10.10/Downloads/iso`, а форма упрощена до одного поля пути. На ВМ хранилище `DSM` перешло в состояние «Доступно», в каталоге появились четыре ISO. Контрольная сумма PXE-меню осталась прежней.

## Профили Windows ISO

На странице «Образы» рядом с найденным Windows x64 ISO из подключённой SMB-папки можно создать профиль. Название и каталог PXE-меню указываются латиницей: встроенный шрифт текущего iPXE-меню не показывает кириллицу. После создания нажмите «Подготовить». Сервис проверит, что ISO не менялся со времени сканирования, смонтирует его только для чтения и скопирует в `/srv/omb/tftp/windows-profiles/<ID>/` только `sources/boot.wim` и два небольших файла запуска WinPE. Полное содержимое ISO остаётся на исходном SMB-хранилище и показывается клиенту через отдельную папку `\\10.30.0.10\ombisos\<ID>` только для чтения. Образ ARM64 в профиле x64 недоступен.

Подготовленный профиль появляется на странице «Меню» как отдельный пункт с каталогом. Публикация перепроверяет исходный ISO, подключение и загрузочные файлы. Прежние пункты Windows 10/11 остаются до клиентской проверки новых профилей. После выбора ручного пункта WinPE самостоятельно подключает ISO и открывает Setup; дальше человек проходит экраны установки вручную.

Для установки этой версии на тестовый сервер применить [миграцию Control](../deploy/sql/2026-10-17-windows-profiles.sql), обновить `omb-agent`, `omb-control` и `omb-boot`, установить `omb-winiso-prepare`, [юнит экземпляра](../deploy/systemd/omb-winiso@.service), два [шаблона запуска](../deploy/boot-assets/windows-profiles/) и секцию `[ombisos]` из [Samba-конфигурации](../deploy/samba/smb.conf). Понадобятся каталоги `/mnt/omb-iso/profiles`, `/srv/omb/tftp/windows-profiles`, `/etc/omb/winiso` и `/usr/share/omb/windows-profiles`. Пароль `omb-iso` остаётся в `/etc/omb/omb-iso-password`; в базу и репозиторий он не попадает.

## Приёмка профилей Windows ISO — 18.10.2026

На тестовом сервере подготовлены два независимых профиля из ISO на SMB-хранилище DSM: `Windows 10x64` (ID 1) и `Windows 11 x64` (ID 2). Оба имеют состояние `ready`; исходные ISO смонтированы только для чтения. В каталоги загрузочных файлов скопированы `boot.wim` и небольшие файлы запуска WinPE, а полные ISO остались на DSM. Активная версия PXE-меню 14 содержит оба новых пункта в каталоге `Windows`; прежние статические пункты пока сохранены.

На ВМ 113 пользователь выбрал каждый новый пункт. В обоих случаях установщик открылся без ручных команд, а после обычного прохождения экранов был виден SATA-диск 70 ГБ. Новый профиль Windows 11 проверен с включённым Secure Boot (`Enabled`). Установку не запускали и диск не изменяли. В журнале Boot подтверждена выдача `winpeshl.ini`, `pxe-setup.cmd` и `boot.wim` для обоих профилей клиенту `10.30.0.19`.

Во время приёмки исправлены две ошибки подготовки: сравнение времени изменения ISO теперь учитывает микросекундную точность каталога, а созданный каталог загрузочных файлов доступен службе Boot. Проверка HTTP после исправления возвращает `200` для файлов профиля из PXE-сети; файл запуска WinPE по-прежнему недоступен из основной сети (`404`). Повторные сбои монтирования ограничены тремя попытками за минуту. Регрессионные тесты, `go test ./...`, `go vet ./...` и `git diff --check` прошли.

Каталог драйверов тогда был отложен; он добавлен 19.10.2026 (см. [руководство Control](control-installation.md#каталог-драйверов-winpe)). Результат последующей проверки Legacy BIOS приведён ниже.

## Сценарии autounattend для одного Windows ISO

Для подготовленного профиля Windows на странице «Образы» можно загрузить несколько готовых XML-файлов. Каждая загрузка создаёт отдельную неизменяемую версию сценария: название и каталог задаются латиницей, размер файла не превышает 1 МиБ. Сервис проверяет структуру XML и корневой элемент `unattend`, но не проверяет настройки Windows Setup. Чтобы изменить сценарий, загрузите новый файл и выберите его вместо прежнего. Повторная загрузка того же XML для того же ISO отклоняется.

На странице «Меню» у одного ISO можно независимо опубликовать ручной пункт и любое число готовых сценариев. Каждый сценарий отображается отдельным пунктом, в том числе в каталоге. При выборе сценария WinPE использует тот же ISO и передаёт выбранный XML установщику через `/Unattend`. Для ручного пункта поведение не меняется. Настройки разметки диска и другие действия в XML выполняет Windows Setup. [Пример, задающий только язык](../examples/windows-answer-language-only.xml), подходит для проверки загрузки файла, но конкретный ISO может потребовать ключ или другие настройки перед продолжением установки. Для теста без записи на диск подготовьте XML со всеми обязательными для этого ISO настройками, но без выбора и разметки диска. Для ISO Windows 11 Pro, требующих ключ, подходит [пример с общим ключом установки и без настроек диска](../examples/windows-answer-key-no-disk.xml): он задаёт язык, публичный общий ключ установки Windows 11 Pro (не активирует систему) и принятие лицензии, поэтому Setup останавливается на ручном выборе диска.

XML может содержать пароли и ключи. Админка не показывает его содержимое после загрузки и не записывает его в журнал аудита. Файл доступен устройствам доверенной сети PXE `10.30.0.0/24` по адресу загрузочного сервера, даже если соответствующий пункт ещё не опубликован. Храните исходный файл у себя и не загружайте секреты, которые нельзя раскрывать этой сети.

Для установки примените [миграцию Control](../deploy/sql/2026-10-18-windows-answers.sql) к базе `omb_control`. Создайте `/srv/omb/tftp/windows-answers` с владельцем `root`, группой `omb-control` и режимом `2750`. Обновите бинарные файлы `omb-agent`, `omb-control`, `omb-boot` и [юнит Agent](../deploy/systemd/omb-agent.service), перечитайте конфигурацию systemd и перезапустите только эти службы. Полные ISO и существующие профили не переподготавливаются. Действующее меню не меняется до следующего нажатия «Опубликовать».

### Установка на тестовом сервере, 18.10.2026

Миграция применена, три службы активны. Перед обновлением сохранены бинарные файлы и дамп базы в `/var/backups/pxe-platform-pre-windows-answers-20261018/`. SHA-256 действующего меню остался `783ca9930d0d93f1184748873ef26008d223ce75776d439be3d58de229119f97`. Существующий `boot.wim` профиля Windows 10 возвращает HTTP 200 из сети PXE. Тестовый XML возвращал HTTP 200 только из сети PXE и HTTP 404 из основной сети, с заголовком `Cache-Control: no-store`. После проверки временный файл удалён.

Первая загрузка XML выявила недостающий путь записи в ограничениях systemd для Agent. Юнит обновлён, после чего прямой запрос на подготовку языкового тестового XML вернул HTTP 204, а созданные файлы получили права `0640 root:pxe-control`. Две неудачные записи без файлов были удалены из базы после проверки, что ни одна версия меню на них не ссылается. Подготовлены профиль с пользовательским XML и отдельный языковой пример; оба пункта появились в опубликованном меню, а их файлы отвечают HTTP 200 из сети PXE и HTTP 404 из основной сети. Языковой пример остановился в Windows Setup из-за отсутствия ключа, который требуется этому ISO. По сообщению пользователя, с полным XML Windows 11 установилась и загрузилась с диска ВМ 113; содержимое XML и секреты не выводились в журнал. После проверки языковой пункт снят с публикации: действующее меню с SHA-256 `f8573c7b6da173184dc7745106f3b082757f1297b1256087dbed018c9c477d33` содержит только рабочий XML-сценарий, а Agent, Control и Boot активны.

## Загрузка ISO через админку — 18.10.2026

На странице «Образы» оператор или администратор выбирает управляемое SMB-хранилище, одну из существующих подпапок (или корень), затем ISO-файл размером до 32 ГиБ. Передача идёт прямо из браузера на выбранную SMB-шару; полный ISO на диске PXE-сервера не создаётся. Индикатор показывает передачу файла, после неё сервер проверяет размер, вычисляет SHA-256 и добавляет запись в каталог. Кнопка «Отменить» прерывает передачу и удаляет временный файл. Готовый файл с тем же именем не перезаписывается. Публикация в PXE-меню остаётся отдельным действием.

Для записи Agent использует сохранённые учётные данные SMB и создаёт вторую точку монтирования `/mnt/omb-smb-upload/<ключ>` с режимом `rw`. Исходная точка `/mnt/omb-smb/<ключ>` остаётся `ro` для чтения и сканирования. Для новой установки создайте каталог `/mnt/omb-smb-upload`, установите обновлённые `omb-agent`, `omb-images`, `omb-control` и обновите юниты [Agent](../deploy/systemd/omb-agent.service) и [Images](../deploy/systemd/omb-images.service), затем перечитайте конфигурацию systemd и перезапустите эти три службы. Право записи на стороне SMB должно быть у ранее введённой учётной записи. При отказе в записи форма сообщит об ошибке; остальные службы продолжат работать.

На тестовом сервере перед обновлением сохранены бинарные файлы и юниты в `/var/backups/pxe-platform-pre-iso-upload-20261018/`. Службы Agent, Images, Control и Boot активны. Для DSM отдельное подключение открылось в режиме `rw`, пробная запись от имени `pxe-images` прошла. Небольшой пробный файл был передан через Images API, его SHA-256 совпал с файлом на DSM, запись появилась в каталоге. Пробный файл и запись затем удалены. Читающее подключение сохранило режим `ro`; действующее PXE-меню не изменилось, SHA-256 остался `f8573c7b6da173184dc7745106f3b082757f1297b1256087dbed018c9c477d33`.

После освобождения места пользователь загрузил через HTTPS-форму `ru-ru_windows_11_consumer_editions_version_26h2_x64_dvd_463bbf21.iso` (8 748 939 264 байта). Размер файла на DSM совпал с каталогом; сервер распознал его как загрузочный ISO 9660. Создан профиль Windows 11 26H2 (ID 3). Control обновлён: после начала подготовки завершает операцию и сохраняет итог даже при разрыве соединения с браузером. Регрессионный тест воспроизводил прежнее зависание в `preparing` и прошёл после исправления. На DSM осталось около 63 ГиБ свободного места.

## Проверка Windows в SeaBIOS — 19.10.2026

На ВМ 112 старый пункт `Windows 10 installer - WinPE`, передающий только `boot.wim`, открыл установщик. Новый профиль `Windows 10x64`, а также старый пункт Windows 11, передававшие дополнительные файлы запуска с параметром iPXE `-n`, останавливались в `wimboot` с сообщениями `Bad CPIO magic` и `FATAL: could not extract initrd files`. Контрольные суммы WIM старого и нового пунктов Windows 10 совпали.

Генератор меню теперь передаёт дополнительные файлы в SeaBIOS командой `initrd <URL> <имя>`, а для UEFI сохраняет прежнюю команду `initrd -n <имя> <URL>`. После обновления Control и повторной публикации меню профиль `Windows 10x64` открыл установщик; пользователь вручную дошёл до списка дисков и увидел SATA-диск ВМ 112 размером 64 ГБ. Профиль `Windows 11 x64` тоже открыл установщик в SeaBIOS, но тот остановился на проверке совместимости компьютера. Для установки Windows 11 Microsoft требует UEFI с поддержкой Secure Boot и TPM 2.0; эта проверка выполнялась на ВМ 113 с OVMF. [Требования Windows 11](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-requirements).

После изменения меню профиль `Windows 10x64` снова открыл установщик на ВМ 113 с OVMF и включённым Secure Boot. На диски тестовых ВМ ничего не записывали. Прежний бинарный файл Control сохранён на сервере в `/var/backups/pxe-platform-bios-initrd-20261019/pxe-control`.
