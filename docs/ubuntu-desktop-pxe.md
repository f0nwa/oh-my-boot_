# Первая загрузка Ubuntu Desktop по PXE

Подготовлен профиль для `ubuntu-26.04.1-desktop-amd64.iso` из подключённой SMB-папки. Boot отдаёт только этот ISO по `/images/ubuntu-desktop.iso`, а извлечённые из него `casper/vmlinuz` и `casper/initrd` — по `/assets/ubuntu/`. В меню Control пункт Ubuntu включается отдельным флажком; публикация сохраняет предыдущую версию для отката. Остальные ISO из SMB-папки по HTTP не выдаются.

После запуска ядра `casper` получает адрес по DHCP, скачивает ISO по HTTP и монтирует его. Это подтверждено разбором `scripts/casper` в initrd данного образа: параметры `iso-url=*.iso` и `url=*.iso` выбирают `NETBOOT=url`, затем `wget` загружает файл. Для ISO размером 6,5 ГБ тестовому клиенту требуется не менее 12 ГБ ОЗУ; для проверки запланировано 16 ГБ. Первая полноценная загрузка клиента ещё требует проверки; успешная выдача HTTP сама по себе не подтверждает запуск Live-системы или работу Secure Boot с этим ядром.

## Настройка

На сервере Boot должен иметь доступ на чтение к выбранному ISO: добавить `pxe-images` в `SupplementaryGroups` юнита `pxe-boot.service`. В `/etc/pxe-platform/boot.env` задать абсолютный путь к файлу:

```ini
PXE_BOOT_UBUNTU_ISO=/mnt/pxe-platform-smb/84e4b95528e2b8c5a405adb7061bc5bf/ubuntu-26.04.1-desktop-amd64.iso
```

В `/etc/pxe-platform/control.env` задать доступный клиентам адрес Boot:

```ini
PXE_CONTROL_BOOT_BASE_URL=http://10.30.0.10:8080
```

Ядро и initrd скопировать из того же ISO в `/srv/pxe/tftp/ubuntu/vmlinuz` и `/srv/pxe/tftp/ubuntu/initrd`; для Secure Boot также скопировать подписанный Ubuntu shim `EFI/boot/bootx64.efi` в `/srv/pxe/tftp/ubuntu/bootx64.efi`. После копирования сравнить SHA-256 исходных файлов и копий. Затем обновить бинарные файлы Boot и Control, перечитать юниты и перезапустить обе службы. До публикации меню проверить `HEAD` для всех URL и диапазонный `GET` ISO. Если SMB-подключение пропадёт, выдача ISO вернёт 404; диагностическое меню Boot продолжит работать.

## Проверка и откат

В HTTPS-админке открыть **Меню**, отметить **Ubuntu Desktop 26.04.1** и нажать **Опубликовать**. Затем запустить тестовую PXE-ВМ с 16 ГБ ОЗУ, выбрать Ubuntu и дождаться рабочего стола Live-системы. Проверить отдельно SeaBIOS, OVMF без Secure Boot и OVMF с Secure Boot. Сетевой доступ к меню до этой проверки уже работает, но совместимость загрузки ядра в трёх режимах пока не установлена.

При неудачной загрузке в админке **Меню → Версии** вернуть прежнюю диагностическую версию. На тестовом сервере прежние бинарные файлы, юнит и настройки сохранены в `/var/backups/pxe-platform-pre-ubuntu-20261016/`. Удаление пункта Ubuntu из меню не требует выключать PXE, DHCP или SMB-хранилище.

## Состояние тестового сервера 16.10.2026

На `192.168.10.135` установлены обновлённые Boot и Control, добавлены настройки и загрузочные файлы. Пять служб активны. `HEAD` вернул 200 для ядра (17 295 752 байта), initrd (95 487 354 байта) и ISO (6 482 409 472 байта). Запрос первого килобайта ISO вернул HTTP 206 и ровно 1024 байта. Страница входа в админку вернула HTTP 200. До публикации пункт Ubuntu отсутствует; SHA-256 действующего меню остался `674ec52f0b9227bd69388dba861da5ecffb470c92da2aa7baf9607085be7c087`.

После публикации пункта первая попытка клиента с Secure Boot остановилась на `Verification failed: Security Policy Violation` при загрузке ядра и initrd. В начальном профиле отсутствовала команда iPXE `shim`. Это соответствует [рекомендации iPXE для Linux с Secure Boot](https://ipxe.org/secboot). В ISO найден Ubuntu `bootx64.efi` с подписью Microsoft и ядро с подписью Canonical. Команда `shim` добавлена в генератор меню; файл из ISO установлен на Boot и отвечает по HTTP 200. Для применения исправления нужно перепубликовать меню в админке; загрузка с включённым Secure Boot после этого ещё не проверена.

При выключенном Secure Boot клиент прошёл запуск ядра, DHCP и начал скачивать ISO. Загрузка оборвалась с `wget: short write: No space left on device` примерно после 850 МБ. На снимке настроек тестовой PXE-ВМ 112 видно 4 ГБ ОЗУ, поэтому ей требуется увеличить память перед повторным тестом. PXE-сервер и SMB-хранилище при этом отвечали; запись Boot показывает запрос ISO от клиента `10.30.0.7`.

После увеличения памяти ВМ 112 до 16 ГБ пользователь подтвердил появление рабочего стола Ubuntu при выключенном Secure Boot. Журнал Boot зафиксировал запросы меню, ядра, initrd и ISO от `10.30.0.7`. Проверка с включённым Secure Boot и обновлённым меню, содержащим команду `shim`, остаётся отдельным шагом.

Обновлённое меню с командой `shim` опубликовано. В следующей попытке ВМ 112 запросила подписанный Ubuntu shim, ядро, initrd и ISO. Это подтверждает, что загрузка прошла прежнюю точку отказа `Security Policy Violation` и дошла до `casper`. Пользователь подтвердил появление рабочего стола при включённом Secure Boot. Таким образом, для этого ISO проверены оба режима OVMF: с Secure Boot и без него. BIOS-загрузка самого ISO ещё не проверена.

При первой проверке Ubuntu через SeaBIOS ядро и initrd загрузились по HTTP, затем iPXE остановился на `shim: command not found`. В BIOS-сборке iPXE этой команды нет. Генератор меню теперь проверяет `${platform}` и вызывает `shim` только на UEFI; SeaBIOS сразу переходит к `boot`. Изменены оба пути генерации меню: обычный и с каталогами. Регрессионные тесты воспроизвели прежний скрипт и прошли после исправления; `go test ./...` и `go vet ./...` также прошли. Обновлённый Control установлен на тестовом сервере 19.10.2026, Boot остался активным. Меню перепубликовано, и HTTP отдаёт ветку с проверкой платформы. В повторной попытке SeaBIOS скачал ISO, после чего пользователь подтвердил появление рабочего стола Ubuntu. Таким образом, для этого ISO проверены SeaBIOS, OVMF с выключенным Secure Boot и OVMF с включённым Secure Boot.
